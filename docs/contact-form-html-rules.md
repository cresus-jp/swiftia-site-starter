# お問い合わせフォーム HTMLコーディング規約（デザイナー向け）

このドキュメントは、Swiftia案件でお問い合わせフォームのHTMLをコーディングする際のルールをまとめたものです。

## 0. このドキュメントの位置づけ

Swiftia案件は以下の3段階で進みます：

1. **デザイナーがHTMLをコーディング**（このドキュメントの対象）
2. 先方にデザインを見せて承認を得る
3. エンジニアがSDK書き換えを行う

このドキュメントが扱うのは**1.の段階**です。書いたHTMLは静的に動くものですが、**後工程でエンジニアがSDK化することを前提に、構造ルールに従っていただく必要があります**。フィールドの並び順・項目数・必須判定は管理画面側の責務なので意識不要ですが（§2-5）、**JSライブラリの初期化コードは「SDKがある前提」での書き方が必要**です。これは別ドキュメント `docs/js-library-rules.md`（全ページ共通）にまとめているので、JSを書く場合は必ず参照してください。

## 1. 全体構造

### 1-1. フォームの基本構造

お問い合わせフォームは、以下の3画面分のHTMLを **1つのファイル内** にすべて記述してください。

| 画面 | 役割 |
|------|------|
| 入力画面 | ユーザーが問い合わせ内容を入力する画面 |
| 確認画面 | 入力内容をユーザーに確認させる画面 |
| 完了画面 | 送信完了後に表示する画面 |

確認画面と完了画面は、入力画面の直後にHTML上で続けて記述します。実際にどの画面を表示するかはエンジニアがSDK化する際に切り替え制御を入れます。

### 1-2. ファイル構成

```
contact.html       ← 入力画面・確認画面・完了画面 をすべて含む
css/...            ← 既存の案件CSSをそのまま利用
js/...             ← 既存の案件JSをそのまま利用（yubinbango等もOK）
```

完了画面を別ページ（`thanks.html` 等）として用意したい場合は、**従来どおり別ファイルとして納品して構いません**。その場合は完了画面のHTML記述は不要です。

## 2. 入力画面のフィールド構造

### 2-1. フィールドタイプ一覧

お問い合わせフォームで使用される入力フィールドは以下の8種類です。**すべてのタイプについて、案件のデザインに沿った1つの見本HTMLを書いてください。**

| タイプ | 用途 | HTML要素 |
|------|------|---------|
| text | お名前、フリガナ、住所等の1行テキスト | `<input type="text">` |
| email | メールアドレス | `<input type="email">` |
| tel | 電話番号、FAX番号 | `<input type="text">`（`type="tel"` でもOK） |
| textarea | お問い合わせ内容など複数行テキスト | `<textarea>` |
| select | 都道府県等の単一選択（プルダウン） | `<select>` |
| radio | カテゴリ選択等の単一選択（ラジオボタン） | `<input type="radio">` |
| checkbox | 複数選択、および同意チェック（単独） | `<input type="checkbox">` |
| file | 履歴書添付、写真送付など | `<input type="file">` |

> **checkbox には 2 つの使い方があります。** 「興味のある商品（複数選択可）」のように選択肢が並ぶものと、「個人情報の取扱いに同意します」のように**チェックボックスが 1 個だけ**のものです。後者も CMS に登録される 1 項目なので、見本として単独のチェックボックスを 1 個書いてください（5 章の静的コンテンツとは別扱いです）。両方使う案件では両方の見本を書きます。

### 2-2. ラベルと必須マーク

各フィールドには以下を含めてください：

- **ラベルテキスト**（例: 「お名前」「メールアドレス」）
- **必須マーク**（必須項目のみ）— `<span class="required-icon">必須</span>` 等のクラス名は案件のデザインに合わせて構いません

### 2-3. エラーメッセージ表示エリア

各フィールドの下に、エラーメッセージを表示するための空の要素を1つ置いてください。

```html
<!-- 例 -->
<div class="form-error">エラーメッセージ</div>
```

- 中身のテキストはダミーで構いません（後工程で動的に書き換えます）
- クラス名は案件のデザインに合わせて構いません
- **同じ構造を全フィールドで統一してください**（あるフィールドだけ別タグや別クラス、はNG）
- エラーが無いときは **SDK が `hidden` 属性で自動的に隠します**（#35）。`::before` の赤バツアイコン等を付けていても空枠は出ません。`.form-error:empty { display:none }` のような指定は不要です

### 2-4. フィールドの実装例（参考）

下記は実装例です。**実際のHTML構造（テーブル/dl/div等）はデザインに合わせて自由に決めて構いません。** 案件のデザインに合わせたHTMLを書いてください。

```html
<!-- text の例 -->
<tr>
  <th>お名前<span class="required-icon">必須</span></th>
  <td>
    <input type="text" name="name" placeholder="例：山田 太郎" class="form-l required">
    <div class="form-error">エラーメッセージ</div>
  </td>
</tr>

<!-- select の例 -->
<tr>
  <th>都道府県</th>
  <td>
    <div class="select-box">
      <select name="state" class="form-s">
        <option value="">選択してください</option>
        <option value="北海道">北海道</option>
        ...
      </select>
    </div>
    <div class="form-error">エラーメッセージ</div>
  </td>
</tr>

<!-- radio の例 -->
<tr>
  <th>お問い合わせ項目<span class="required-icon">必須</span></th>
  <td>
    <ul class="radio-list">
      <li><label class="radio"><input type="radio" name="categories" value="お仕事のご依頼"><span>お仕事のご依頼</span></label></li>
      <li><label class="radio"><input type="radio" name="categories" value="採用について"><span>採用について</span></label></li>
    </ul>
    <div class="form-error">エラーメッセージ</div>
  </td>
</tr>

<!-- textarea の例 -->
<tr>
  <th>お問い合わせ内容<span class="required-icon">必須</span></th>
  <td>
    <textarea name="contents" placeholder="お問い合わせ内容をご記入ください" class="form-h required"></textarea>
    <div class="form-error">エラーメッセージ</div>
  </td>
</tr>

<!-- file の例 -->
<tr>
  <th>履歴書<span class="required-icon">必須</span></th>
  <td>
    <input type="file" name="resume" class="form-file required">
    <p class="form-note">PDF / JPEG / PNG （最大 10MB）</p>
    <div class="form-error">エラーメッセージ</div>
  </td>
</tr>
```

`file` フィールドは原則 **1つのフィールドあたり1ファイル** を選択できる UI を想定しています。許可される拡張子・最大サイズは管理画面で設定され、SDK 化の際に `accept` 属性として自動付与されます。デザイナーはダミーの説明文（「PDF / JPEG / PNG（最大 10MB）」など）を**入れても入れなくても構いません**（実値はエンジニアが SDK 化時に管理画面の設定に合わせて整えます）。

### 2-5. してはいけないこと

- **同じタイプのフィールドを複数異なるデザインで書かないでください**（例: お名前は `<table>`、メールアドレスは `<dl>` のような混在NG）
- **`name` 属性の値は仮で構いません。最終的な値はエンジニアが決めます**
- **必須／任意の判定（`required` クラス等）も仮で構いません。最終的な必須判定は管理画面で設定されます**
- **フィールドの並び順や項目数も仮で構いません。最終的な並び順・項目は管理画面で設定されます**

つまり**デザイナーが書くのは「各フィールドタイプの見た目」のみ**で、フィールド一覧の構成や必須判定は後で管理画面で変更されます。

## 3. 確認画面

入力画面と同じレイアウトで、入力欄ではなく入力された値だけを表示する画面を作ってください。

```html
<!-- 例 -->
<tr>
  <th>お名前</th>
  <td>山田 太郎</td>
</tr>
<tr>
  <th>メールアドレス</th>
  <td>yamada@example.com</td>
</tr>
<tr>
  <th>履歴書</th>
  <td>resume.pdf (1.2 MB)</td>
</tr>
```

- 各フィールドの値を表示する場所には**仮の値**を入れておいてください
- 確認画面の下部には「**戻る**」ボタンと「**送信する**」ボタンの2つを配置してください
- `file` フィールドの値は「ファイル名 (サイズ)」の形でテキスト表示されます（プレビューは MVP 範囲外）

## 4. 完了画面

送信成功後に表示するメッセージを記述してください。

```html
<!-- 例 -->
<div class="contact-thanks">
  <p>お問い合わせありがとうございました。</p>
  <p>3営業日以内にご返信いたします。</p>
</div>
```

別ファイル（`thanks.html` 等）として納品しても構いません。

## 5. 静的コンテンツ（個人情報取扱い等）

フォーム内に「個人情報の取り扱いについて」等の説明文を含める場合は、**通常のHTMLとして自由に記述してください**。これらの静的コンテンツはそのまま保持されます。

```html
<section>
  <h3>個人情報の取り扱いについて</h3>
  <p>当社は、個人情報保護の重要性を認識し...</p>
</section>
```

> **「同意します」のチェックボックス自体は静的コンテンツではありません。** 上の説明文（規約本文）は静的でよいのですが、チェックボックスは CMS に登録される入力項目です。静的な `<input type="checkbox">` として書くと、SDK 化後に**同意の有無が送信内容に含まれません**（記録が残らない）。2-1 の checkbox 見本として書いてください。

### 5-1. 項目ごとの補足文について

「全角カタカナでご入力ください」のような**項目ごとの補足文は、現時点では CMS から出せません**。SDK 化の際に落ちてしまうため、次のいずれかで対応してください。

- `placeholder` で表現する（例: `placeholder="例：ヤマダ タロウ"`）
- フォーム全体にかかる注意書きとして、フィールドの外（上記のような静的セクション）に置く
- どうしても項目の直下に出したい場合は、**事前にエンジニアへ相談**する

なお `file` フィールドの許可拡張子・最大サイズの案内文は、管理画面の設定と食い違う原因になるため、ベタ書きしないでください（2-4 参照）。

## 6. CSS・既存JSライブラリの扱い

### 6-1. CSSは自由に書いてOK

各フィールドのデザインは案件のデザインに合わせて自由に記述してください。SDK化後もCSSはそのまま動作します。

#### 画面遷移時の自動スクロール（固定ヘッダーがある場合）

SDKは画面が切り替わるとき（入力→確認 / 確認→戻る / 確認→完了）に、フォーム先頭へ自動でスクロールします（初回の入力表示時は除く）。また、**入力エラーで確認画面に進めなかったとき**は、最初のエラー項目へ自動でスクロールします（ページ下部の送信ボタンからでもエラーに気付けます）。**固定ヘッダーがある場合だけ**、隠れないように対象へ `scroll-margin-top` を1行足してください（無ければ対応不要）。

```css
swiftia-contact-form { scroll-margin-top: 80px; } /* 画面遷移時：フォーム先頭の固定ヘッダー対策 */
/* 入力エラー時にエラー項目が固定ヘッダーへ隠れる場合は、入力欄にも同様に指定 */
.form input, .form select, .form textarea { scroll-margin-top: 80px; }
```

- 別の要素（フォーム上の見出し等）へスクロールしたいときは `<swiftia-contact-form scroll-target="#form-heading">` を指定（画面遷移時のみ。エラースクロールは常に該当エラー項目が対象）。
- 自動スクロールを無効化したいときは `<swiftia-contact-form scroll="off">`（画面遷移・エラーの両方が無効になります）。

#### フォーム装飾の標準化（Enter送信抑止 / textarea 自動可変・#37）

よくあるフォーム装飾は SDK オプションや CSS で賄えます。**`form.js` 等で自前実装する必要はありません**。

- **Enter キーでの誤送信を防ぐ**: `<swiftia-contact-form enter-submit="off">` を付けると、単一行の `<input>` での Enter による送信を抑止します（`<textarea>` の改行・送信ボタンの Enter は通常どおり）。
- **textarea の高さ自動可変**: CSS の `field-sizing: content` で実現できます（入力量に応じて高さが伸縮）。

```css
/* textarea を入力量に合わせて自動で伸縮させる */
textarea {
  field-sizing: content;
  min-height: 6em; /* 初期の高さ */
  max-height: 20em; /* 伸びすぎ防止（任意） */
}
```

> `field-sizing` は新しめのプロパティです。未対応ブラウザでは無視され、`min-height` で確保した固定高さの通常の textarea として表示されます（実害なし）。JS での高さ調整が必須要件の場合のみ、`docs/js-library-rules.md` に従って冪等な初期化関数を用意してください。

### 6-2. 既存JSライブラリ（yubinbango等）

郵便番号→住所自動補完（yubinbango）等、**CSSクラスでフックするタイプ**のライブラリは、必要なクラス名（`h-adr`, `p-postal-code`, `p-region`, `p-locality`, `p-street-address`, `p-country-name` 等）をそのまま付与してください。クラスはSDK化後も保持されます。

```html
<form class="h-adr">
  <span class="p-country-name" style="display: none">Japan</span>
  ...
  <input type="text" name="postal_code" class="p-postal-code">
  ...
  <select name="state" class="p-region">...</select>
  ...
</form>
```

### 6-3. JSライブラリ・独自スクリプトの初期化（必読）

スライダー・ライトボックス・フォーム装飾など、**JSで要素を探して初期化するタイプ**の処理（`new Swiper(...)` や、ページ読み込み時に `querySelectorAll` でフォーム項目を拾う独自スクリプト等）は、SDKがフォーム項目を**後から描画する**ため、従来どおり「ロード時に一度だけ」の書き方では動きません。

**初期化は「名前付き・スコープ可能・冪等な関数」で書いてください。** 詳細とサンプルは `docs/js-library-rules.md`（全ページ共通の規約）を参照してください。

## 7. 納品時のチェックリスト

- [ ] 入力画面・確認画面・完了画面の3画面（または別納品の完了ページ）が揃っている
- [ ] フィールドタイプごと（text / email / tel / textarea / select / radio / checkbox / file）の見本がある（案件で `file` を使わない場合は省略可）
- [ ] 同意チェックボックスを静的な飾りではなく checkbox タイプの見本として書いている（5 章）
- [ ] 項目ごとの補足文を `placeholder` かフォーム外の静的セクションに寄せている（5-1）
- [ ] 必須マークのデザインがある
- [ ] エラーメッセージ表示エリアが各フィールドに統一フォーマットで配置されている
- [ ] 確認画面に「戻る」「送信する」ボタンがある
- [ ] 既存JSライブラリ用のクラス（必要な場合）が付与されている
- [ ] JSライブラリ・独自スクリプトの初期化が `docs/js-library-rules.md` の規約（名前付き・スコープ可能・冪等な関数）に沿っている
