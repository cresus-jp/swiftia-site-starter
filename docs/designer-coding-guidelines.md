# サイト制作コーディングガイドライン（デザイナー向け）

顧客サイトのテンプレートリポジトリ **swiftia-site-starter** をベースに静的 HTML を制作・納品するための総合ガイドラインです。

## 0. このガイドラインについて

### 0-1. 対象読者と位置づけ

顧客サイトの HTML / CSS / JavaScript を制作するデザイナー・コーダー向けです。案件は次の 3 段階で進みます。

```
① デザイナーが静的 HTML を制作・納品   ← このガイドラインの範囲
② 顧客がデザインを承認
③ エンジニアが Swiftia SDK に書き換え（CMS 連携化）
```

皆さんが書いた HTML は、③ の工程で「1 件目のマークアップをテンプレートとして機械的に変換」されます。このガイドラインの規約は、**後工程を壊さない・手戻りを生まない**ためのルールです。「なぜそう書くのか」も併記しているので、理由ごと覚えてください。

### 0-2. 関連ドキュメント

本ガイドラインは全体の共通規約を扱い、詳細は責務ごとに分かれた各ドキュメントに委ねます。

| ドキュメント | 内容 | いつ読むか |
|---|---|---|
| [GitHub はじめてガイド](github-first-steps.md) | アカウント作成・招待の受諾・Git インストール・最初のクローン | GitHub が初めての人は一番最初に |
| [Git かんたんマニュアル（Mac 編）](git-guide-mac.md) / [（Windows 編）](git-guide-windows.md) | ふだんの作業手順（pull・commit・push） | 案件に入る前に必ず |
| [お問い合わせフォーム HTML コーディング規約](contact-form-html-rules.md) | フォームページの入力・確認・完了画面の書き方 | フォームページを作るとき |

## 1. 全体の流れ（案件開始から公開まで）

1. **リポジトリの受け取り** — コーディネーターが管理画面から案件リポジトリを自動生成します（GitHub org `cresus-jp` 配下・private）。あなたは**コラボレーター（push 権限）として招待**されるので、招待メールを承諾してください。リポジトリはテンプレート（swiftia-site-starter）から複製済みで、公開の仕組みが最初から入っています
2. **制作** — リポジトリを clone し、ローカルで静的 HTML を制作。`main` ブランチへ push すると**自動でテスト用サイト `https://案件名.pages.dev` に反映**されます（FTP 不要・ブランチを切る必要もありません）
3. **納品・顧客承認** — テスト用 URL で顧客がデザインを確認
4. **SDK 化（エンジニア工程）** — エンジニアが同じリポジトリでお知らせ・実績・フォーム等を CMS 連携に書き換えます
5. **本番公開** — 独自ドメインを接続して公開

> **テスト用 URL の注意**: `*.pages.dev` には検索エンジン向けの noindex が自動で付与されますが、URL を知っていれば誰でも閲覧できます。顧客情報を含む制作物を扱っている意識を持ち、URL をむやみに共有しないでください。

## 2. リポジトリの構成 — どこに何を置くか

clone した直後のリポジトリは次の構成です。

| パス | 役割 | 扱い |
|---|---|---|
| `index.html` | トップページ（仮の「準備中」ページ） | **自分の HTML で置き換える** |
| `404.html` | Not Found ページ | **案件のデザインに合わせて作り直す**（⛔ **削除禁止**。理由は 2-3） |
| `assets/css/` `assets/js/` `assets/images/` | CSS・JS・画像の置き場所 | **ここに配置する** |
| `functions/_middleware.js` | SEO/OGP メタタグの自動注入・sitemap/robots 配信の実体 | ⛔ **編集・削除禁止** |
| `_routes.json` | 上記の仕組みの動作範囲の定義 | ⛔ **編集・削除禁止**（相談時を除く） |
| `.github/workflows/deploy.yml` | push → 自動デプロイの定義 | ⛔ **編集・削除禁止** |

### 2-1. 配置ルール

- **HTML はリポジトリ直下から配置**します（ビルドや書き出し工程はなく、リポジトリの中身がそのまま Web サイトとして配信されます）
- **CSS・JS・画像・フォントは `assets/` 配下**にまとめてください
  ```
  assets/
  ├── css/        … reset.css, common.css, style.css など
  ├── js/         … ライブラリ・自作 JS
  ├── images/     … ページ名ごとのサブディレクトリで整理（後述）
  └── fonts/      … Web フォント
  ```
- `favicon.ico` はリポジトリ直下に置きます
- **`assets/` 以外の静的ディレクトリを新設したいときは、事前にエンジニアへ相談**してください（`_routes.json` への追記が必要になり、忘れると配信コストが無駄に増えます）

### 2-2. 画像ディレクトリの整理

```
assets/images/
├── common/      … ロゴ・ヘッダー/フッター等の全ページ共通
├── ogp/         … OGP 画像（1200×630 推奨）
├── dummy/       … CMS 差し込み予定箇所のダミー写真
├── home/        … トップページ専用
├── about/       … ページごとに 1 ディレクトリ
└── ...
```

`images/` と `img/` のような**用途の重複するディレクトリを二重に作らない**でください（過去案件で実際に混乱の元になりました）。

### 2-3. 置いてはいけないファイル・消してはいけないファイル

- **`sitemap.xml` / `robots.txt` を置かない** — システムが自動生成・配信します。実ファイルを置くとそちらが優先され、CMS 連動の自動更新が止まります
- **`404.html` を消さない** — デザインに合わせて中身を作り直すのは歓迎ですが、ファイル自体を削除すると次の2つが同時に壊れます（2026-08 の移行検証で実際に踏んだ挙動です）
  - 存在しないURLへのアクセスに**トップページが 200 で返る**（検索エンジンから見て soft 404。存在しないURLがすべてトップページ扱いになる）
  - **`sitemap.xml` / `robots.txt` の自動配信が止まる** — システムは「そのパスが 404 だったとき」に自動生成した内容を返す設計なので、404 が返らなくなると起動しない
- **Swiftia SDK の `<script>` タグ** — SDK の組み込みはエンジニア工程です。デザイン段階で入れると二重作業になります
- **PSD・AI・動画などの元データ、100MB 超のファイル** — リポジトリには書き出し済みの HTML/CSS/JS/画像のみを入れます
- **ビルドツール（Sass・Vite・webpack 等）の設定や成果物** — リポジトリ直下がそのまま配信されるため、素の CSS / JS だけをコミットします。どうしてもプリプロセッサを使いたい場合は事前にエンジニアへ相談してください

## 3. URL・ファイル名の設計規約

### 3-1. ページのファイル配置

| ページ種別 | 配置 | URL |
|---|---|---|
| トップ | `index.html` | `/` |
| 固定ページ（会社概要など） | `company/index.html` | `/company/` |
| **一覧ページ**（お知らせ・実績など） | `news/index.html` | `/news/` |
| **詳細ページ** | `news/detail.html` | `/news/detail?id=1` |
| お問い合わせ | `contact/index.html` | `/contact/` |

- **CMS 連携するセクション（お知らせ・実績・コラム等）は、必ず「`セクション名/index.html`（一覧）＋ `セクション名/detail.html`（詳細）」の 2 ファイル構成**にしてください
- **理由**: CMS 側に登録できる詳細ページの URL パターンは全セクション共通で 1 つだけ（`/{セクション}/detail?id={番号}`）です。`news-detail.html` のような形でも、**全セクションが同じ形に揃っていれば**設定はできますが、セクションごとに形が混在すると 1 つのパターンで表せず、はみ出したセクションはサイトマップ生成から外す運用になります。新規案件は上記の 2 ファイル構成に統一してください
- 記事 1 件ごとに HTML ファイルを作る方式（`news/101/index.html` など)は禁止です。詳細ページは 1 枚だけ作り、`?id=` で記事を切り替える前提でデザインします

### 3-2. 内部リンクとパスの書き方

- **内部リンク・アセット参照は、すべてルート絶対パス（先頭 `/`）で書きます**

  ```html
  <!-- ✅ よい -->
  <a href="/company/">会社概要</a>
  <link rel="stylesheet" href="/assets/css/common.css" />
  <img src="/assets/images/common/logo.png" alt="株式会社サンプル" />

  <!-- ❌ わるい: 相対パス（ディレクトリ階層が変わると全ページ壊れる） -->
  <a href="company.html">会社概要</a>
  <img src="images/logo.png" alt="" />
  ```

- **内部リンクに `.html` を付けない**でください。配信システムが拡張子なし URL に正規化（リダイレクト）するため、`.html` 付きリンクは無駄な転送を挟みます
- CMS 連携ページへのリンクはクエリパラメータ形式に揃えます: 詳細 `/news/detail?id=1`、カテゴリ絞り込み `/news/?category=2`、ページ送り `/news/?page=2`

> **ローカル確認の注意**: ルート絶対パスは HTML ファイルをダブルクリックで開くと効きません。VS Code の「Live Server」拡張などの簡易ローカルサーバーで確認するか、push してテスト用 URL で確認してください。

## 4. HTML 共通規約

### 4-1. head の雛形（全ページ必須）

すべてのページの `<head>` に、次のタグを**静的に**書いてください。

```html
<!doctype html>
<html lang="ja">
<head>
  <meta charset="utf-8" />
  <meta name="viewport" content="width=device-width, initial-scale=1" />
  <title>ページ名 | サイト名</title>
  <meta name="description" content="このページの説明文（80〜120字目安）" />
  <meta property="og:title" content="ページ名 | サイト名" />
  <meta property="og:description" content="このページの説明文" />
  <meta property="og:image" content="https://仮ドメイン.example.com/assets/images/ogp/ogp.png" />
  <meta property="og:url" content="https://仮ドメイン.example.com/このページのパス" />
  <meta property="og:type" content="website" />
  <link rel="canonical" href="https://仮ドメイン.example.com/このページのパス" />
  <link rel="icon" href="/favicon.ico" />
  <!-- 以下 CSS 読み込み -->
</head>
```

**なぜ全部書くのか（重要）**: 本番公開後、CMS のデータ（記事タイトルなど）を `title` / `description` / `og:title` / `og:description` に自動で焼き込む仕組みが動きます。この仕組みは **`og:title` / `og:description` を「既存タグの書き換え」でしか処理できません**。タグ自体が無いページは、本番で OGP が空のまま公開されます。**空でもよいので必ずタグを置いてください。**

あわせて次の点にも注意してください。

- 詳細ページ（`<swiftia-detail>` を使うページ）に限り、`canonical` / `og:url` が記事ごとの URL に、`og:image` が記事の主画像（`image1`）に自動で書き換わります（#76）。一覧ページはこれまでどおり自動書き換えの**対象外**で、静的に書いた値がそのまま使われます
- 詳細ページでも**書き換わるのは既存タグのみ**です。仕組みはタグを新規生成しないため、`4-1` の head 雛形どおり `og:image` / `og:url` / `canonical` のタグ自体は必ず静的に書いてください。主画像が無い記事では静的に書いた `og:image` がそのまま使われるので、フォールバックとして妥当な値にしておきます
- 本番ドメイン確定前は仮ドメインで統一しておき、本番昇格時にエンジニアと一括置換します
- 一覧ページ（`/news/` など、クエリなしの URL）は自動注入の対象外で、**静的に書いた title / description がそのまま検索結果に出ます**。仮テキストのまま納品しないでください
- この自動注入は本番ドメインでのみ動きます。**テスト用 URL（`*.pages.dev`）で反映されないのは正常**です
- メタタグの確認は、開発者ツールではなく「ページのソースを表示（view-source）」で行ってください

### 4-2. 文書構造

- **`<h1>` を全ページに 1 つだけ**置いてください（トップページも例外ではありません。ロゴ画像しかない場合でもヒーローの見出しを `<h1>` にします）
- `<header>` → `<main>` → `<footer>` の共通骨格を全ページで統一します
- パンくずは全ページ同じマークアップで統一します。詳細ページのパンくずは**記事名の部分だけ**が CMS の値に差し替わるので、記事名を単独の要素にしてください（詳しくは 5-5）
- すべての `<img>` に `alt` を書きます（装飾画像は `alt=""`）

### 4-3. class 命名

- **見た目ではなく意味・役割ベース**で命名します（`.news-card-title` ○ / `.red-text` ✕）
- 方式は「ページ・セクション名を先頭に置いたハイフン連結」（`news-card-title`）でも BEM（`news-card__title`）でも構いませんが、**サイト内で 1 方式に統一**してください
- **JS から操作する要素には `js-` プレフィックスのクラスを付け、スタイル用クラスと分離**します（スタイル調整で JS が壊れる事故を防ぐため）
- 状態表現のクラス（`.active` 等）を**カテゴリ絞り込みの選択状態に使わない**でください（理由は [5-3](#5-3-カテゴリ絞り込みナビ) 参照）
- typo に注意してください。誤字クラス名は HTML と CSS の両方に定着し、後から直せなくなります（実例: `probrem` が全ページに残存した案件あり）

### 4-4. インデント・フォーマット

- インデントは**半角スペース 2 個・タブ・スペース 4 個のいずれかに統一**します。ファイルごと・ファイル内での混在は禁止です
- エディタ設定を揃えるため、リポジトリ直下に `.editorconfig` を置くことを推奨します

### 4-5. 画像

- `<img>` には **`width` / `height` 属性を必ず指定**します（読み込み中のレイアウトのガタつき＝CLS を防ぐため。CSS で `max-width: 100%; height: auto;` を併用すればレスポンシブと両立できます）
- ファーストビュー以外の画像には **`loading="lazy"`** を付けます
- SP / PC の画像出し分けは `<picture>` + `<source media>` で行います

  ```html
  <!-- ✅ よい: 表示する方だけダウンロードされる -->
  <picture>
    <source media="(max-width: 767px)" srcset="/assets/images/home/hero-sp.jpg" />
    <img src="/assets/images/home/hero.jpg" width="1600" height="900" alt="" />
  </picture>

  <!-- ❌ わるい: 2枚とも常にダウンロードされる -->
  <img src="hero.jpg" class="d-none d-md-block" alt="" />
  <img src="hero-sp.jpg" class="d-md-none" alt="" />
  ```

## 5. CMS 連携ページ（一覧・詳細）のマークアップ規約 ★最重要

お知らせ・実績・コラムなど、後から CMS 連携になるページの書き方です。エンジニアは**あなたが書いた 1 件目のマークアップをテンプレートとして変換**するため、ここのルールが崩れていると手戻りが最も大きくなります。

### 5-1. 一覧は「同一マークアップ × 3〜4 件」で書く

- カード・行を **3〜4 件、完全に同じ HTML 構造・同じクラス構成**で繰り返してください（見た目の確認のために複数件、変換のために同一構造）
- **1 件目が「正」としてテンプレート化**されます。「1 件目だけ大きい」等のデザインは事前にエンジニアへ相談してください
- ダミーテキストは連番でわかりやすく（`サンプルニュースタイトル1`、`サンプルニュースタイトル2`…）、ダミー画像は `/assets/images/dummy/` を参照します

### 5-2. 値は必ず「独立した要素」に入れる

CMS の値（日付・タイトル・カテゴリ名など）は、1 つの値 = 1 つの要素になるように書きます。

```html
<!-- ✅ よい -->
<li class="news-card">
  <a href="/news/detail?id=1">
    <img class="news-card-thumb" src="/assets/images/dummy/news-1.jpg" width="400" height="300" alt="" />
    <time class="news-card-date" datetime="2026-01-01">2026.01.01</time>
    <span class="news-card-category">お知らせ</span>
    <span class="news-card-new">NEW</span>
    <h2 class="news-card-title">サンプルニュースタイトル1</h2>
  </a>
</li>

<!-- ❌ わるい: 日付とタイトルが 1 つの要素に混ざっている -->
<li><a href="news-detail.html"><p>2026.01.01 サンプルニュースタイトル1</p></a></li>
```

- 「NEW」バッジのように**記事によって出たり出なかったりする要素も、独立した要素**にしてください（後工程で「条件付き表示」の属性を被せるだけで済みます）
- テーブル型の一覧の場合、繰り返し単位は `<tr>` で完結させてください（1 記事が複数の `<tr>` にまたがる構造は不可）

### 5-3. カテゴリ絞り込みナビ

- `ul > li > a` のフラットな構造で書きます。リンク先は `/news/?category=1` の形式です
- 先頭に「すべて」リンク（`/news/?` または `/news/`）を置きます
- **選択中スタイルは `.active` クラスではなく、`aria-current` 属性で書きます**。CMS 連携後のシステムはクラスを付与せず `aria-current="page"` だけを自動制御するためです

  ```css
  /* ✅ よい */
  .news-category a[aria-current="page"] { background: #0066cc; color: #fff; }

  /* ❌ わるい: SDK 化後、永遠に選択状態にならない */
  .news-category a.active { ... }
  ```

- 「すべて」ボタンに**無条件の背景色を付けない**でください（常に選択中に見えるバグになります。選択表現は必ず `aria-current` で)
- 子カテゴリがある場合は、`li` の中に同じ構造の `ul` を入れ子にします

### 5-4. ページ送り（ページネーション)

こだわりがなければ、**ページャの HTML は作り込まなくて構いません**（CMS 連携時に「前へ / 1 2 3 … / 次へ」が自動生成されます）。

ただし既定のページャは**サイトの CSS が届かない別の仕組み**で描画されます。そのため次のルールがあります。

> **ページャのデザインに合わせた CSS を書いたなら、HTML も必ず書いてください。** CSS だけ書いて HTML を省くと、書いた CSS は一切使われません（既定の素朴な見た目のまま公開されます）。

独自デザインにする場合は、`<a href="/news/?page=2">` のような**素朴なリンクの並び**で書いてください（複雑な入れ子や JS 依存の構造は変換コストが跳ね上がります）。このとき次の 4 つを**すべて**置いておきます。

```html
<nav class="pagination" aria-label="ページ送り">
  <a class="pagination-link pagination-prev" href="/news/?page=1">前へ</a>
  <a class="pagination-link" href="/news/?page=1" aria-current="page">1</a>
  <a class="pagination-link" href="/news/?page=2">2</a>
  <a class="pagination-link" href="/news/?page=3">3</a>
  <span class="pagination-ellipsis">…</span>
  <a class="pagination-link" href="/news/?page=10">10</a>
  <a class="pagination-link pagination-next" href="/news/?page=2">次へ</a>
</nav>
```

| 置くもの | 省くと起きること |
|---|---|
| 「前へ」 | 2 ページ目以降で前に戻るリンクが出ない |
| 「次へ」 | 次のページに進めない |
| 省略記号（`…`） | 総ページ数が 8 以上になると「…」が出るが、CSS が当たらず崩れる |
| 現在ページの表現 | 今どのページを見ているか分からない |

- **1 ページ目・最終ページで不要な要素は、後工程で自動的に消えます。** 「1 ページ目のデザインだから『前へ』は要らない」と省略しないでください（消えるものは書いておくのが正解です）
- **現在ページのスタイルは `.current` クラスと `aria-current="page"` の両方に当てておいてください。** カテゴリナビ（5-3）は属性だけですが、ページャは現時点でクラスも使われます

  ```css
  /* ✅ よい: どちらでも効く */
  .pagination-link.current,
  .pagination-link[aria-current="page"] { background: #0066cc; color: #fff; }

  /* ❌ わるい: 属性だけだと現在ページに色が付かない（実案件で発生） */
  .pagination-link[aria-current="page"] { background: #0066cc; }
  ```

- 記事が少ないうちはページャ自体が表示されません（1 ページに収まる間は出ない仕様です）。**納品時に見えていなくても、上記が揃っているかは目視で確認**してください

### 5-5. 詳細ページ

- タイトル・日付・カテゴリ・本文・画像は**それぞれ単独の要素**に分けます（5-2 と同じ原則）
- 本文エリアは `<div class="article-body">` のように**クラスを 1 つ付けた箱**で囲み、その中身は要素セレクタでスタイルを当てます（重要なので 5-6 に分けて説明します）
- 「前の記事 / 次の記事」リンクは `<a>` 1 個ずつのシンプルな構造にします（先頭・末尾の記事では**要素ごと消える**前提でデザインしてください）
- パンくずは「**固定の階層 ＋ 記事名**」の形で書き、記事名を単独の要素にします（差し替わるのは記事名だけです）

  ```html
  <ol class="breadcrumb">
    <li class="breadcrumb-item"><a href="/">ホーム</a></li>
    <li class="breadcrumb-item"><a href="/news/">お知らせ</a></li>
    <li class="breadcrumb-item">サンプルニュースタイトル1</li>  <!-- ここが記事名に差し替わる -->
  </ol>
  ```

  記事のカテゴリをパンくずに挟みたい場合（`ホーム › お知らせ › カテゴリA › 記事名`）は、**事前にエンジニアへ相談**してください。現時点では「固定の階層 ＋ 記事名」の形にのみ対応しています

- 添付ファイルのダウンロードボタンは `li > a` を 1 組だけ書き、ファイル種別ごとの見た目の違いはクラスの付け替えで表現できるようにします（種別は `pdf` / `word` / `excel` / `powerpoint` / `file` の 5 つ）

  ```html
  <li><a href="#" class="btn-file pdf">資料ダウンロード<span class="btn-file-size">(1.2MB)</span></a></li>
  ```

  ボタンの文字は CMS に登録された**実ファイル名**に差し替わります。**サイズ表記を入れるかは事前にエンジニアへ相談**してください（CMS から渡る数値の書式が決まっており、`(1.2MB)` の形にできない場合があります）。入れる場合は上記のように独立した `<span>` にしてください

- 詳細ページの `canonical` / `og:url` / `og:image` は**記事ごとに自動で書き換わります**（#76。1 枚の HTML で全記事を表示しますが、SDK が記事ごとの URL・主画像に同期します）。静的に書く値は**書き換わる前提のフォールバック**として妥当なものにしてください（`og:image` は主画像が無い記事でそのまま使われるため、`?id=1` 固定や仮の1枚を書くのではなく、セクションを代表する画像にしておくと安全です）

### 5-6. 本文エリア（詳細ページの本文）のスタイル

詳細ページの本文は、CMS のリッチテキストエディタが出力した HTML が**そのまま**流し込まれます。CMS 側にはクラス名を付ける手段がないため、入ってくるのは**クラスの付いていない生の要素**（`<h2>` `<p>` `<ul>` …）だけです。

一方サイト側はリセット CSS（destyle / normalize 系）で `h1`〜`h6` の `font-size` / `font-weight` を `inherit` に、`ul` / `ol` の `list-style` を `none` に、`p` の `margin` を 0 に潰しているのが普通です。放置すると **CMS で設定した見出しが本文と見分けの付かない状態で公開されます**（2026-08 に実案件で発生。運用者からは「CMS で設定した見出しが反映されない」という不具合報告として上がってきます）。

**この事故自体は SDK 側で止まるようになりました。** SDK が本文の入った箱に `data-swiftia-html` を付け、リセットで消えた既定（見出しのサイズ・太さ、段落の余白、リストのマーカー、引用の罫線、水平線の余白、リンクの下線）を復旧するスタイルを自動で当てます。**ただしこれは「リセットで消えた既定の復旧」であって、デザインではありません。** サイトの見た目に合わせるのは従来どおり制作側の仕事です。

#### 書き方 — 箱をクラスで囲み、中は要素セレクタで指定する

```html
<div class="article-body">{{本文}}</div>
```

```css
/* ❌ わるい: CMS の見出しには当たらない（クラスが付かないため） */
.article-body .title-band { ... }

/* ❌ わるい: 素の型セレクタだけでは SDK の既定スタイルに負ける */
h2 { font-size: 1.5rem; }

/* ✅ よい: 本文エリアのクラスでスコープし、その中は要素セレクタで書く */
.article-body h2 { ... }
.article-body h3 { ... }
.article-body p { margin-bottom: 1em; }
```

SDK の既定は `[data-swiftia-html] h2` という形（**属性1つ + 型1つ**）で `<head>` の先頭に入ります。したがって **`.article-body h2` のように「クラス + 型」で書けば必ず上書きできます**。逆に素の `h2 { }` だけでは詳細度が足りず負けるので、本文用のスタイルは必ずクラスでスコープしてください。

#### 当てる対象の一覧

CMS の本文エディタから出力されうる要素は下表で**打ち止め**です。裏を返せば、**この表を全部埋めれば本文エリアは完成**します。

| CMS のボタン | 出力される HTML | 当てておくもの |
|---|---|---|
| 見出し2 / 見出し3 | `<h2>` `<h3>` | 文字サイズ・太さ・上下マージン |
| （通常の本文） | `<p>` | `margin-bottom` |
| 箇条書き / 番号リスト | `<ul>` `<ol>` `<li>`（**項目の中身は `<p>` で包まれて出力されます**） | マーカー、`padding-left`、`li > p { margin-bottom: 0 }`、入れ子リストの余白 |
| 太字 / 斜体 | `<strong>` `<em>` | 既定で効きます（見出しの中に入ったときの太さだけ確認） |
| 文字色 / 背景色 | `<span style="color:…">` `<mark style="background-color:…">` | `mark` の文字色（指定しないとブラウザ既定色に落ちます） |
| リンク | `<a href>` | 色・下線 |
| 引用 | `<blockquote>` | 罫線・背景・内側の余白 |
| 水平線 | `<hr>` | 上下マージン |
| YouTube | `<div data-youtube-video><iframe width="640" height="480">` | `iframe { width: 100%; height: auto; aspect-ratio: 16 / 9 }`（属性の 640px のままだとスマホで横にはみ出す） |

- **画像・表は本文からは入りません**（画像は「画像1〜5」、ファイルは「添付ファイル」の項目として別枠で渡ります）。ただし過去データ由来の `<img>` が混ざることはあるので、`img { max-width: 100%; height: auto }` だけは当てておくと安全です

#### 落とし穴

- **`::before` でマーカーを出すなら `list-style: none` も明示してください。** リセット任せにすると、SDK の既定が当てる `disc` / `decimal` が残ってマーカーが二重になります（`• ・箇条書き` のような表示。実案件で発生）

  ```css
  /* ✅ よい: 「・」で出すなら list-style を自分で切る */
  .article-body ul { padding-left: 0; list-style: none; }
  .article-body ul > li { position: relative; padding-left: 1.2em; }
  .article-body ul > li::before { position: absolute; left: 0; content: "・"; }
  ```

- **本文の見出しは記事タイトルより 1 段小さく**します。記事タイトルと同じ大きさだと階層が読めません
- **先頭・末尾の余白を潰します** — `.article-body > *:first-child { margin-top: 0 }` / `.article-body > *:last-child { margin-bottom: 0 }`。本文が見出しで始まる記事は珍しくないので、これが無いと記事ごとに天地の余白がばらつきます
- **見た目はサイトの既存パーツと揃えます** — `.title-band` / `.title-underline` などの数値をそのまま要素セレクタ側にも書いてください。独自の値を作ると記事だけデザインから浮きます
- 本文の箱には**その値だけ**を入れてください（`<div class="article-body">{{本文}}</div>`）。`<p>{{本文}}</p>` のように段落やインライン要素で包むと、中に見出しやリストが入って HTML として不正になります

CMS の編集画面では見出しが大きく表示されます。納品前に、ダミーの本文へ上表の要素をひととおり入れて目視してください。

### 5-7. 「0 件のとき」「取得できなかったとき」の見た目も用意する

CMS 連携後は、**記事が 1 件も無い状態**や、**通信エラーでデータが取れない状態**が実際に起こります。カテゴリで絞り込んだ結果が 0 件になることもあるため、珍しい状態ではありません。

納品 HTML にこの受け皿が無いと、後工程でエンジニアが独自のマークアップと CSS を足すことになり、**サイトのデザインから浮いた見た目になります**。一覧ページと詳細ページに 1 つずつ用意してください。

```html
<!-- 一覧ページ: 該当する記事が 0 件のとき -->
<p class="list-empty">該当する記事はありません。</p>

<!-- 詳細ページ: 記事が見つからない・データの取得に失敗したとき -->
<p class="detail-error">
  お探しの記事は見つかりませんでした。<br />
  <a href="/news/">お知らせ一覧へ戻る</a>
</p>
```

- 通常の表示では邪魔になるので、**コメントで「0 件時に表示」と明記**しておけば十分です（納品時に消さないでください）
- カード一覧を `display: grid` / `flex` で組んでいる場合、この要素が**横 1 行を占有する**指定（`grid-column: 1 / -1` など）も当てておいてください。付け忘れると 1 カラム目に潰れて表示されます

### 5-8. JavaScript でコンテンツを組み立てない

- 記事データ・カード・リスト項目などの**コンテンツはすべて HTML に直接書いてください**。JS で `innerHTML` や `createElement` を使って組み立てたコンテンツは、後工程でテンプレート化できません
- アコーディオンの開閉・スライダー・スクロール演出など「挙動」のための JS は OK です（書き方は [JS ライブラリ実装規約](js-library-rules.md) に従うこと）

## 6. お問い合わせフォーム

フォームページの詳細規約は **[お問い合わせフォーム HTML コーディング規約](contact-form-html-rules.md)** に従ってください。ここでは特に事故が多いポイントだけ再掲します。

- 入力フィールドは 8 タイプ（text / email / tel / textarea / select / radio / checkbox / file）**各 1 見本**でよい。並び順・項目数・必須の最終決定は管理画面側の責務
- **同じタイプのフィールドは全て同一の HTML 構造**で書く（お名前は `<table>`、メールは `<dl>` のような混在は禁止）
- 各フィールドに「ラベル＋必須マーク」「エラーメッセージ用の要素（例: `<div class="form-error">`）」を必ず添える。エラー要素を CSS の `:empty` などで隠さない
- **`name` 属性の値は仮でよいが、フィールド間で重複させない**（radio / checkbox の選択肢間で共有するのは正しい）。過去案件で「法人名」と「お名前」が両方 `name="name"` になっており、送信すると片方が消える実バグがありました
- **「個人情報の取扱いに同意します」のような同意チェックボックスも、CMS に登録される 1 項目**です。静的な飾りとして書くのではなく、checkbox タイプの見本として**単独のチェックボックス 1 個**で書いてください（選択肢が複数並ぶ checkbox とは別扱いになります）
- **項目ごとの補足文（「全角カタカナでご入力ください」等）は CMS の項目設定（補足説明）に引き継げます。** 各項目の直下に**統一したクラス名の要素**（例: `<p class="form__hint">`）で書いてください（項目ごとに書き方をバラつかせない）。フォーム全体にかかる注意書きは、フィールドの外に置けばそのまま残ります
- `text` タイプの項目に付けた `autocomplete`（`organization` / `postal-code` / `street-address` 等）は、**CMS の項目設定に引き継げます**（SDK 化時にエンジニアが `{{autocomplete}}` 変数としてテンプレートへ組み込みます）。納品 HTML には従来どおり適切な値を付けてください
- 確認画面・完了画面も規約どおり用意する（原則 1 ファイルに続けて記述）

## 7. CSS 規約

### 7-1. 読み込み順

head 内の CSS は「触らないもの → ページ固有ライブラリ → 共通 → ページ別 → 補助」の順で読み込みます。

```html
<!-- General CSS: リセット・フレームワーク（変更しない） -->
<link rel="stylesheet" href="/assets/css/reset.css" />
<!-- Page CSS: そのページだけが使うライブラリ CSS（例: swiper-bundle.min.css） -->
<!-- Common CSS: 共通レイアウト → ページ固有 → パーツ → ユーティリティ → 印刷 -->
<link rel="stylesheet" href="/assets/css/base.css" />
<link rel="stylesheet" href="/assets/css/common.css" />
<link rel="stylesheet" href="/assets/css/style.css" />
<link rel="stylesheet" href="/assets/css/module.css" />
<link rel="stylesheet" href="/assets/css/utility.css" />
<link rel="stylesheet" href="/assets/css/print.css" media="print" />
```

- ファイル分割の粒度は案件に合わせて構いませんが、**CSS 冒頭の構成コメントと実態を必ず一致させてください**（存在しないファイルの説明コメントが全ファイルにコピペされ続けた実例があります）

### 7-2. ブレークポイント

- 使用する値を**サイト内で固定のセットに統一**します（Bootstrap 併用時はその標準値 576 / 768 / 992 / 1200 / 1400 のみ）
- `max-width: 374px` や `1599px` のような場当たりな値を増やさないでください

### 7-3. セレクタ設計 — DOM 構造に依存させない

CMS 連携時、一覧やナビの周囲には目に見えないカスタム要素（`<swiftia-list>` 等）が挿入されます。レイアウト上は透明ですが、**DOM 構造に依存したセレクタは影響を受けます**。

```css
/* ❌ 避ける: 直接の親子関係・位置に依存 */
.news-list > li { ... }
.news-list li:nth-child(odd) { ... }

/* ✅ よい: クラス直指定・gap で余白 */
.news-card { ... }
.news-list { display: grid; gap: 24px; }
```

### 7-4. CMS 連携を見越した小ワザ（任意）

- 固定ヘッダーがある場合、エラー項目への自動スクロールがヘッダーに隠れないよう `scroll-margin-top` を指定しておく
- `textarea` の高さ自動可変は JS ではなく `field-sizing: content` で
- ページャは HTML も自分で書くのが確実です（理由は 5-4）。HTML を省いて既定のページャに任せる場合、装飾は `swiftia-pagination::part(button)` / `::part(button current)` で当てます（SDK 化後にエンジニアと調整）

## 8. JavaScript 規約

書き方の詳細は **[JS ライブラリ実装規約](js-library-rules.md)** に従ってください。要点は次のとおりです。

### 8-1. 使用ライブラリ

公式サポートスタックは **jQuery / Swiper（スライダー）/ lightcase（ライトボックス）/ AOS または GSAP ScrollTrigger（スクロール演出）/ matchHeight（高さ揃え）/ yubinbango（住所自動入力）** です。これ以外のライブラリ（fancybox・colorbox・slick 等）を使いたい場合は、**必ず事前にエンジニアへ共有**してください。

### 8-2. 読み込み順と配置

`</body>` 直前に「共通ライブラリ → 自作共通 → ページ固有」の順で読み込みます。

```html
<!-- General Library -->
<script src="/assets/js/jquery-3.5.1.min.js"></script>
<script src="/assets/js/aos.js"></script>
<!-- Original Script -->
<script src="/assets/js/common.js"></script>
<!-- Page Script -->
<script src="/assets/js/swiper-bundle.min.js"></script>
<script src="/assets/js/news.js"></script>
```

### 8-3. 初期化の 3 原則（違反すると SDK 化で全滅します）

CMS 連携後は、コンテンツが**ページ読み込みより後に、しかも何度も**描画し直されます。初期化コードは必ず次の 3 条件を満たしてください。

1. **名前付き関数にする** — `new Swiper(...)` をトップレベルやインライン `<script>` にベタ書きしない
2. **スコープ引数を取る** — `document` 全体ではなく、引数で渡された範囲だけを初期化できる形にする
3. **冪等にする** — 同じ関数を何度呼んでも壊れない（再実行前に既存インスタンスを破棄、jQuery イベントは名前空間付き `.off().on()`）

`var ham = $('.header-hamburger');` のような**トップレベルでの DOM 直接取得＋即時実行**は、「script が body 末尾にある」ことへの暗黙依存であり非推奨です。ヘッダー等の静的部分でも、名前付き関数＋呼び出しの形に揃えてください。

### 8-4. 納品物の衛生

- **どの HTML からも読み込まれていない JS ファイルを納品しない**（過去案件で未使用ファイル 5 本が納品され、うち 1 本は読み込むと共通 JS と関数名が衝突する状態でした）
- JS が参照するクラス名が HTML に実在するか、納品前に確認する（テンプレート流用時の消し忘れが頻発ポイント）

## 9. やってはいけないこと（総まとめ）

| ❌ 禁止事項 | 理由 |
|---|---|
| `functions/` `_routes.json` `.github/` の編集・削除 | サイト公開・SEO 注入・デプロイの仕組みが壊れる |
| `sitemap.xml` / `robots.txt` の設置 | 自動配信が止まる |
| `404.html` の削除 | 未存在URLにトップページが 200 で返り（soft 404）、`sitemap.xml` / `robots.txt` の自動配信も止まる |
| Swiftia SDK の `<script>` タグを貼る | SDK 組み込みはエンジニア工程（二重作業になる） |
| ビルドツールの導入 | リポジトリ直下がそのまま配信される前提 |
| JS でコンテンツ DOM を組み立てる | テンプレート化できない |
| カテゴリ絞り込みの選択状態を `.active` クラスで当てる | カテゴリ・絞り込みナビは `aria-current="page"` だけが自動制御される（ページャは 5-4 のとおり両方に当てる） |
| ページャの CSS だけ書いて HTML を省く | 既定のページャにはサイトの CSS が届かず、書いた CSS が使われない |
| 0 件表示・取得失敗表示を用意しない | 後工程で足したマークアップがデザインから浮く |
| 詳細ページの本文エリアのスタイルを用意しない | CMS から入るのはクラスの付かない生の要素。SDK の既定スタイルで最低限は読めるが、記事だけデザインから浮く（5-6） |
| 本文エリアのスタイルを素の型セレクタ（`h2 { }`）だけで書く | 詳細度が足りず SDK の既定スタイルに負ける。必ず本文エリアのクラスでスコープする（5-6） |
| 記事ごとの静的 HTML ファイル生成 | 詳細は `detail?id=` の 1 枚で切り替える設計 |
| 相対パスでのリンク・アセット参照 | ディレクトリ構成の変更で全ページ壊れる |
| 実在の企業名・住所・電話・写真の無断使用 | テスト用 URL でも外部からアクセス可能 |

## 10. 納品前チェックリスト

### 全ページ共通
- [ ] `<head>` に title / description / og:title / og:description / og:image / og:url / canonical が全ページ揃っている
- [ ] 一覧ページ・固定ページの title / description が仮テキストのままになっていない
- [ ] `<h1>` が全ページに 1 つだけある
- [ ] 内部リンク・アセット参照がルート絶対パス（先頭 `/`）で、`.html` 付きリンクがない
- [ ] 画像に `width` / `height` / `alt` があり、ファーストビュー以外は `loading="lazy"`
- [ ] インデントが統一されている

### CMS 連携ページ
- [ ] 一覧の繰り返しが 3〜4 件、完全に同一構造になっている
- [ ] 値（日付・タイトル・カテゴリ等）がそれぞれ独立した要素に入っている
- [ ] 詳細ページが `セクション名/detail.html` で、リンクが `?id=` 形式になっている
- [ ] カテゴリ選択状態の CSS が `aria-current` ベースになっている
- [ ] ページャに「前へ」「次へ」「省略記号」「現在ページ」が揃っていて、現在ページの CSS が `.current` と `aria-current` の両方に当たっている
- [ ] 一覧の 0 件表示・詳細の取得失敗表示が用意され、グリッド／フレックス内で横 1 行を占有する指定が当たっている
- [ ] 詳細ページのパンくずが「固定の階層 ＋ 記事名」で、記事名が単独の要素になっている
- [ ] 詳細ページの本文エリアが「クラス + 要素セレクタ」で指定され、5-6 の表の要素（`h2` `h3` `p` `ul` `ol` `li` `blockquote` `hr` `a` `mark` `iframe`）すべてに見た目が付いている
- [ ] 本文のリストを `::before` で装飾している場合、`list-style: none` を明示している（マーカー二重表示の防止）
- [ ] フォームの `name` 属性に重複がない（[フォーム規約](contact-form-html-rules.md)のチェックリストも実施）
- [ ] 同意チェックボックスを静的な飾りではなく checkbox タイプの見本として書いている

### JS・アセット
- [ ] 初期化コードが 3 原則（名前付き・スコープ可能・冪等）を満たしている（[JS 規約](js-library-rules.md)のチェックリストも実施)
- [ ] 未使用の JS / CSS / 画像ファイルが残っていない
- [ ] 公式スタック外のライブラリを使う場合、エンジニアに共有済み

### リポジトリ
- [ ] `functions/` `_routes.json` `.github/` が元のまま残っている
- [ ] `404.html` が残っている（中身をデザインに合わせるのは可・ファイルの削除は不可）
- [ ] `sitemap.xml` / `robots.txt` / SDK スクリプトタグを置いていない
- [ ] push して `https://案件名.pages.dev` で表示確認した
